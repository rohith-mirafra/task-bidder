Task Bidder — process reference

How a task moves through the system

One state machine (open → claimed → in_progress → pending_review → done), four actors, and one outside system. This is what actually happens between a creator typing a title and a worker banking the points.

Creatorposts tasks with mandatory required_skills, vets their own tasks' completion Workersees only eligible tasks, claims, works, submits for review Adminis_admin flag — refreshes/edits eligibility, overrides claims MS Teamsexternal — one-way, filtered to eligible workers

Admin is a flag, not a role

It can sit on a Creator account, a Worker account, or both, and more than one person can hold it. It unlocks the Workers page, eligibility refresh/edit, and the reassign override — nothing about creating tasks.

Approval is owner-only, not any creator

A worker can only push a task to pending_review. Only the task's own creator can approve it into done or reject it back to in_progress — a different, narrower creator power than reassignment below.

Reassignment is a full override

Any Creator or Admin can hand a claimed, in-progress, or pending-review task to a different worker, or reopen it — the explicit way to override a worker's bid, regardless of the eligibility snapshot or who owns it.

Refresh is global, not per-task

required_skills is set once, by the task's own creator. Who currently satisfies it is recomputed only when an Admin clicks Refresh once on the Workers page — which updates every gated task in that pass, never automatically and never one at a time.

Notifications are best-effort

Every matching URL gets tried on every event. A dead or unreachable one is logged and skipped — it never blocks the action that triggered it, for anyone else on the list.

Admin can edit criteria directly, per task

Beyond the global refresh, an Admin can rewrite one task's required_skills inline on its row — that always force-recomputes just that task's snapshot immediately, independent of the next global refresh.
